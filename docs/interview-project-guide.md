# Sentinel 面试项目详细文档

## 1. 项目定位

### 1.1 一句话介绍

Sentinel 是一个面向企业安全运营场景的多 Agent 安全事件智能研判平台，围绕安全情报采集、事件结构化提取、语义去重、风险评估、知识召回和报告生成，形成了一条完整的自动化分析闭环。

### 1.2 项目背景

在传统安全运营场景里，安全团队通常需要同时关注 RSS 安全公告、GitHub Security Advisory、NVD 漏洞库、厂商通告等多个情报源。问题主要有三类：

- 情报源分散，人工收集成本高
- 同类漏洞和公告重复出现，人工归并效率低
- 高危事件需要快速判断影响范围、优先级和处置建议，人工分析耗时长

这个项目的核心目标，是把这些原本依赖人工完成的步骤，尽量转成可自动执行、可视化追踪、可沉淀复用的系统能力。

### 1.3 项目价值

- 提升安全情报的自动采集与统一管理能力
- 缩短安全事件从发现到研判的时间
- 通过 AI 辅助降低一线分析人员的重复劳动
- 通过 Milvus 构建历史案例记忆，增强后续研判的一致性和可复用性

## 3. 系统整体架构

### 3.1 架构分层

项目整体可以分成五层：

- 采集层：负责对外部安全情报源做订阅、抓取和标准化转换
- 业务层：负责订阅管理、事件管理、报告管理、抓取日志管理
- AI 分析层：负责多 Agent 编排、结构化提取、去重、风险评估、报告生成
- 存储层：MySQL 负责结构化业务数据，Milvus 负责语义检索与历史事件记忆
- 展示层：前端负责控制台、趋势图、事件列表、SSE 实时研判过程展示

### 3.2 核心数据流

完整主链路如下：

1. 用户在订阅管理页面添加安全情报源
2. 系统按 Cron 定时调度，或用户手动触发抓取
3. 采集器从 RSS、GitHub、NVD 等来源拉取数据
4. 系统按 `unique_hash` 对事件去重后写入 MySQL
5. 用户在事件分析页面触发多 Agent 研判
6. 系统按“数据采集 -> 智能提取 -> 去重 -> 风险评估 -> 解决方案生成”顺序执行
7. 分析过程通过 SSE 实时推送到前端
8. 处理后的事件和 AI 分析结果可索引到 Milvus
9. 用户可基于时间范围或指定事件生成安全报告
10. 报告支持 Markdown、HTML、JSON 导出

## 4. 主要模块说明

### 4.1 订阅管理模块

职责：

- 管理外部安全情报源
- 配置源类型、地址、调度表达式、状态
- 支持启用、暂停、禁用、删除
- 支持手动抓取
- 展示抓取统计与抓取日志

支持的源类型：

- RSS
- GitHub Repo / GitHub Security Advisory
- NVD
- 预留了 WebHook、CVE、Threat Intel、Vendor Advisory、Attack Activity 等扩展类型

### 4.2 事件管理模块

职责：

- 展示安全事件列表
- 支持按严重级别、状态、关键字筛选
- 支持批量更新状态
- 支持查看事件详情
- 支持单事件 AI 分析

### 4.3 多 Agent 事件分析模块

职责：

- 对一批事件做自动化研判
- 在前端以流式方式展示每个 Agent 的执行状态
- 输出风险概览、关键事件、处置建议

当前流水线包含 5 个核心阶段：

- 数据采集 Agent
- 智能提取 Agent
- 去重 Agent
- 风险评估 Agent
- 解决方案 Agent

### 4.4 向量检索与知识库模块

职责：

- 将已处理事件及分析结果做向量化索引
- 支持历史相似事件检索
- 支持内部知识文档检索
- 为解决方案生成和复杂事件分析提供 RAG 能力

### 4.5 报告管理模块

职责：

- 基于事件时间范围或指定事件生成安全分析报告
- 支持日报、周报、月报、漏洞告警、威胁简报、自定义报告
- 支持查看、删除、导出

### 4.6 AI Chat / Supervisor 模块

职责：

- 提供面向运维或安全分析的 AI 对话入口
- 支持工具调用
- 支持内部文档查询、事件查询、报告查询等能力

这一块可以作为扩展能力讲，但面试时建议优先把“事件闭环”作为主线。

## 5. 核心业务流程

### 5.1 情报采集流程

1. 创建订阅源
2. 配置 `source_type`、`source_url`、`cron_expr`
3. 调度器按时间触发任务
4. 根据订阅类型分发到对应 Fetcher
5. Fetcher 拉取外部数据并转换成统一的 `SecurityEvent`
6. 通过 `unique_hash` 做幂等去重
7. 写入事件表，同时记录抓取日志
8. 更新订阅的 `last_fetch_at` 和 `total_events`

### 5.2 多 Agent 研判流程

1. 用户在页面选择分析模式
2. 后端查询指定事件或最近事件
3. 提取 Agent 调用大模型做结构化抽取
4. 去重 Agent 对提取后的事件做语义层去重
5. 风险评估 Agent 输出风险分数、严重级别、建议和影响因素
6. 解决方案 Agent 结合工具能力和历史知识生成处置建议
7. 流程中的每一步通过 SSE 发给前端
8. 前端实时渲染拓扑、日志和风险面板

### 5.3 RAG 检索流程

1. 事件处理完成后，将标题、描述、CVE、厂商、产品、AI 分析结果拼装为索引文本
2. 生成 embedding 后写入 Milvus
3. 新事件分析时，使用当前查询或事件描述做向量召回
4. 返回相似历史事件及元数据
5. 供解决方案 Agent 参考历史案例和经验

### 5.4 报告生成流程

1. 用户选择报告类型和时间范围
2. 后端查询匹配事件
3. 按报告类型拼接 Prompt
4. 调用大模型生成正文
5. 从正文中提取摘要
6. 保存报告记录和统计结果
7. 支持后续查看、列表轮询和导出

## 7. 重点技术设计

### 7.1 为什么采集层使用统一 Fetcher 接口

项目里对不同外部源定义了统一的 `Fetcher` 接口，每个来源只需要实现：

- `Fetch(ctx, sub)`
- `Type()`

这样做的好处：

- 新增数据源时不需要改动主流程
- 业务层只依赖统一结果 `[]SecurityEvent`
- 易于做调度器接入和后续扩展

### 7.2 为什么事件去重同时做多层处理

系统实际有两层去重思路：

- 入库前基于 `unique_hash` 做幂等去重
- 多 Agent 研判阶段再做一次语义去重

这样做的原因：

- 第一层解决“同一源重复抓取”的问题
- 第二层解决“不同源对同一漏洞重复报道”的问题

### 7.3 为什么用 SSE 展示分析过程

这里选择 SSE 而不是轮询，核心考虑是：

- 多 Agent 流程天然是阶段式输出
- 前端只需要单向实时接收结果
- SSE 实现比 WebSocket 更轻，适合当前场景

### 7.4 为什么需要 Milvus

仅靠 MySQL 只能做精确查询和条件过滤，无法支持：

- 相似安全事件检索
- 历史案例复用
- 内部知识文档召回

因此引入 Milvus，配合 embedding 做语义层检索，增强解决方案生成的上下文质量。

### 7.5 为什么用多 Agent 而不是单次 Prompt

核心原因是把复杂问题拆小：

- 提取阶段专注结构化
- 去重阶段专注过滤重复
- 风险阶段专注评分和建议
- 解决方案阶段专注检索增强和推理

这种拆分比一个大 Prompt 更容易调试、更容易定位问题，也更适合可视化展示。

## 11. 我负责的功能详细文档

这一部分建议你重点背熟。面试时，不要只说“我参与了”，而是要围绕“为什么做、怎么做、解决了什么问题、权衡了什么”来讲。

### 11.1 功能一：安全情报订阅采集链路

#### 功能目标

把多个外部安全情报源统一接入系统，支持定时抓取、手动抓取、事件去重入库和抓取日志沉淀。

#### 我负责的内容

- 订阅模型设计
- Fetcher 抽象设计
- RSS / GitHub / NVD 采集能力接入
- 抓取服务封装
- 去重入库逻辑
- 抓取日志记录
- 订阅状态和统计更新

#### 方案设计

我把采集能力拆成三层：

- 订阅配置层：负责源地址、源类型、状态、调度参数
- Fetcher 实现层：不同源各自解析，但统一输出 `SecurityEvent`
- 采集服务层：负责统一调度、去重、日志和统计

这种设计的优点是，数据源扩展只影响 Fetcher 层，不影响业务主链路。

#### 技术细节

- 使用统一 `Fetcher` 接口屏蔽不同外部源差异
- RSS 采集兼容 RSS 和 RDF 两种格式
- GitHub 采集同时覆盖 Release 和 Security Advisory
- NVD 采集按时间窗口拉取最近漏洞，并解析 CVSS、CVE、CPE
- 入库前通过 `unique_hash` 做幂等判断，避免重复事件
- 每次抓取都记录 `FetchLog`，包含耗时、数量、失败原因
- 抓取完成后回写订阅的最近抓取时间和累计事件数

#### 难点与解决方案

难点 1：不同来源数据结构差异大

解决方式：

- 统一映射到 `SecurityEvent`
- 在源侧尽量补齐 `title`、`description`、`source_url`、`event_time`
- 额外补充 `cve_id`、`cvss_score`、`affected_vendor`、`affected_product`

难点 2：重复数据容易污染后续分析

解决方式：

- 通过 `unique_hash` 做第一层去重
- 把去重前置到落库逻辑，避免脏数据积累

难点 3：采集失败后难以排查

解决方式：

- 对每次任务记录抓取日志
- 错误、耗时、事件数都入库，便于排查外部源问题

#### 这块你在面试里可以怎么说

“我负责的是系统最前面的情报采集链路。因为这个项目本质上要解决的是多源安全情报统一接入的问题，所以我先把数据源抽象成统一 Fetcher 接口，再在服务层处理去重、日志和统计。这样后续扩展新的情报源时，只需要新增一个 Fetcher，不需要动主流程。”

#### 面试官可能追问

问：为什么不直接在每个采集器里自己写入数据库？

答：

- 那样会把采集和业务逻辑耦合在一起
- 后续加日志、加去重、加统计会在每个采集器里重复写一遍
- 统一收口到服务层更利于维护

### 11.2 功能二：多 Agent 安全事件研判流水线

#### 功能目标

把安全事件从“原始公告”转化成“结构化结论 + 风险评估 + 处置建议”，并能把全过程实时展示给用户。

#### 我负责的内容

- 多 Agent 流水线整体串联
- SSE 实时流式输出
- 事件选择模式设计
- 提取、去重、风险评估、解决方案各阶段的结果串联
- 前端实时展示对接

#### 方案设计

我把研判流程拆成五步：

1. 数据采集：确定待分析事件集
2. 智能提取：抽取标题、CVE、严重级别、影响产品等结构化信息
3. 去重过滤：清理多源重复事件
4. 风险评估：输出风险分数、严重级别和推荐动作
5. 解决方案：结合历史案例和知识库给出处置建议

核心思路不是追求“一个 Prompt 做完所有事情”，而是把复杂问题拆成多个职责单一的阶段。

#### 技术细节

- 后端接口通过 `text/event-stream` 向前端实时推送阶段状态
- 每个阶段都输出 `agent_start`、`agent_progress`、`agent_complete`
- 前端按事件流实时驱动拓扑图、日志面板和结果面板
- 支持按最近事件、今日事件、指定事件三种模式分析
- 对模型失败场景做了降级处理，保证链路不中断

#### 难点与解决方案

难点 1：AI 流程可观测性差

解决方式：

- 采用显式阶段划分
- 每个 Agent 的状态和消息都流式发给前端
- 让用户能看到“分析到哪一步了”

难点 2：大模型步骤失败可能导致整条链路中断

解决方式：

- 提取失败时回退到原始事件字段
- 评估失败时给默认风险分数和人工复核建议
- 保证流程具备可用的最小输出

难点 3：前端需要实时感知阶段变化

解决方式：

- 使用 SSE 替代轮询
- 事件协议统一，包括类型、Agent 名称、状态、消息、时间戳、数据负载

#### 这块你在面试里可以怎么说

“这块我重点做的是把 AI 研判流程工程化。相比单次大模型调用，我更关注链路的拆分、状态可见性和失败兜底。因为在业务上，用户最关心的不是模型内部怎么推理，而是当前分析到了哪一步、出了问题能不能继续、最后有没有稳定可用的结果。”

#### 面试官可能追问

问：为什么这里用 SSE，不用 WebSocket？

答：

- 这个场景主要是服务端单向持续推送
- SSE 更轻量，实现成本更低
- 不需要额外维护双向连接和复杂协议

### 11.3 功能三：事件知识库与 Milvus 语义召回

#### 功能目标

将历史安全事件和分析结论沉淀成可复用的语义知识库，在新事件研判时提供相似案例召回能力。

#### 我负责的内容

- 事件索引文本设计
- 向量入库逻辑
- 相似事件检索工具封装
- 与解决方案 Agent 的联动

#### 方案设计

这部分不是把原始事件直接丢到向量库，而是先组织成适合检索的文本，包括：

- 标题
- CVE
- 严重级别
- 厂商和产品
- 描述
- AI 分析结论

这样做的原因是，单纯只存标题或只存描述，召回质量会比较差；把结构化字段和 AI 结论一起拼进去，能提升相似度检索的上下文完整性。

#### 技术细节

- 事件索引文本长度做了截断控制，避免超长内容影响存储和检索成本
- 元数据里附带 `event_id`、`severity`、`cve_id`、`risk_score`
- 检索工具返回的不只是正文，还能带回元数据用于后续推理
- 相似事件工具被解决方案 Agent 当作工具能力调用，而不是硬编码到主流程里

#### 难点与解决方案

难点 1：什么内容适合进向量库

解决方式：

- 优先放对后续研判有帮助的信息
- 保留结构化字段和 AI 总结
- 对正文做长度控制

难点 2：检索结果怎么被下游有效使用

解决方式：

- 把召回能力封装成工具
- 让 Agent 在需要时自主调用
- 返回结果时保留可解释元数据

#### 这块你在面试里可以怎么说

“我做这块的时候，重点不是简单接一个向量库，而是考虑什么数据值得沉淀、怎样组织内容能提升召回效果，以及召回结果怎样真正参与后续决策。最后的实现是把历史事件和 AI 结论一起写入 Milvus，再由解决方案 Agent 在需要时调用相似事件检索工具。”

#### 面试官可能追问

问：为什么不用 MySQL 做 like 检索？

答：

- MySQL 更适合精确查询和过滤
- 对相似漏洞、相似描述、相似处置建议这类语义场景效果有限
- Milvus 更适合做历史案例召回

### 11.4 功能四：研判可视化与报告输出

#### 功能目标

把后端 AI 分析结果变成前端可视化的研判过程和可落地的报告产物。

#### 我负责的内容

- 事件分析页的实时交互设计
- 阶段状态驱动的前端展示
- 风险概览与结果面板联动
- 报告生成和导出能力

#### 方案设计

我把用户体验拆成两个阶段：

- 分析过程中，重点解决“用户知道系统正在做什么”
- 分析结束后，重点解决“用户能沉淀什么结果”

对应到产品能力上，就是：

- 分析过程有拓扑图、进度日志、统计栏、结果栏
- 分析结束后能直接生成报告并导出

#### 技术细节

- 前端通过 `fetch + ReadableStream` 读取 SSE 流
- 按后端事件类型更新 Zustand 状态
- 风险评估完成后立即刷新右侧结果面板
- 报告模块支持分页、筛选、详情查看、导出
- 报告导出支持 Markdown、HTML、JSON

#### 难点与解决方案

难点 1：流式数据在前端如何组织

解决方式：

- 约定统一的数据协议
- 通过 `agent`、`status`、`type` 三个字段驱动界面状态

难点 2：分析结果结束后如何沉淀

解决方式：

- 增加报告模块
- 将 AI 生成内容、摘要、统计信息持久化
- 支持导出，方便交付和复盘

#### 这块你在面试里可以怎么说

“我不只是把后端能力接出来，而是重点考虑用户怎么理解这条 AI 链路。因为如果 AI 只是给一个最终结果，用户会缺少信任感。所以我把研判过程做成了可视化的多阶段展示，结束后再衔接报告生成，让结果既可看、也可保存、还能导出。”

## 12. 项目亮点总结

面试时可以概括成下面四点：

- 不是简单 CRUD 项目，而是“采集 + AI + 检索 + 可视化 + 报告”的完整闭环
- 把多源安全情报统一抽象成标准事件模型，具备扩展能力
- AI 研判流程做了工程化拆解，强调可观测性和失败兜底
- 通过 Milvus 做历史案例记忆，提高分析结果的复用价值

## 13. 项目中的真实权衡

这一段很重要。面试官通常喜欢问你是否真正理解系统，而不是只会背功能。

### 13.1 为什么先做统一模型，再做智能分析

因为如果数据模型不统一，后续所有 AI 分析都会变成针对每种源单独处理，维护成本很高。

### 13.2 为什么多 Agent 不是越多越好

Agent 数量越多，流程越复杂，调试成本也越高。这个项目选择 5 个核心阶段，是在可解释性和复杂度之间做平衡。

### 13.3 为什么报告生成不直接实时流式返回

报告的核心目标是沉淀结构化结果，而不是展示推理过程，所以更适合异步生成并存档。

### 13.4 这个项目当前的不足

可以比较诚实地说：

- 多数 AI 结果质量仍依赖模型输出稳定性
- 去重目前是“哈希 + 一层语义去重”，更复杂的跨源聚类还可以继续做
- 采集源类型虽然做了扩展设计，但当前真正落地的源还有限
- 没有看到更完整的权限、多租户和审计闭环

## 14. 面试官可能会问到的问题

### 14.1 项目理解类

#### 问题 1：这个项目到底解决了什么问题？

回答思路：

- 解决多源安全情报分散的问题
- 解决人工筛选、去重、评估效率低的问题
- 通过 AI 和向量检索提高自动化研判能力

#### 问题 2：为什么把它定义成多 Agent，而不是普通 AI 功能？

回答思路：

- 因为流程里包含多个职责不同的阶段
- 需要把结构化提取、去重、风险评估、解决方案生成拆开
- 拆分后更容易调试、观测和扩展

#### 问题 3：项目的主业务闭环是什么？

回答思路：

- 订阅情报源
- 定时采集事件
- 去重入库
- AI 研判
- 历史召回
- 报告生成

### 14.2 后端设计类

#### 问题 4：为什么要抽象 Fetcher 接口？

回答思路：

- 屏蔽不同外部源差异
- 方便扩展新源
- 主流程只关心统一输出

#### 问题 5：采集服务为什么不直接并发无限开 goroutine？

回答思路：

- 外部源不稳定，盲目并发会放大超时和失败
- 当前用了简单并发限制思路，避免资源失控
- 如果进一步优化，可以接 worker pool 和限流

#### 问题 6：如何保证重复事件不会重复入库？

回答思路：

- 基于 `unique_hash` 做幂等判断
- 在插入前查询是否已存在
- 这是第一层去重

#### 问题 7：如果不同源报道的是同一个漏洞，哈希去重怎么办？

回答思路：

- 哈希只能解决同一条数据重复抓取
- 跨源重复需要依赖后续语义去重
- 所以系统设计了第二层 AI 去重

#### 问题 8：为什么分析接口要单独走 SSE？

回答思路：

- 需要阶段性输出
- 用户希望实时看到进度和结果
- SSE 很适合这种服务端单向推送场景

#### 问题 9：如果某一步大模型调用失败怎么办？

回答思路：

- 做降级兜底
- 用原始事件字段回填
- 给默认风险分数和人工复核建议
- 避免整条链路直接失败

### 14.3 AI / RAG 类

#### 问题 10：为什么要做结构化提取？

回答思路：

- 原始公告格式不统一
- 前端展示、统计、风险评估都依赖结构化字段
- 结构化后更利于存储和检索

#### 问题 11：为什么要引入 Milvus？

回答思路：

- 解决相似事件召回问题
- 辅助解决方案生成
- 提升历史案例复用能力

#### 问题 12：你是怎么设计向量入库内容的？

回答思路：

- 不只存标题
- 把标题、CVE、严重级别、厂商、产品、描述、AI 结论拼成统一文本
- 同时存元数据，便于召回后解释

#### 问题 13：为什么不是所有步骤都依赖向量检索？
